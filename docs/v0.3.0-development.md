# Fun Ground v0.3.0 development plan

## Release process
1. Develop only on `codex/fun-ground-v0.3.0-foundation`; keep `main` untouched.
2. Preserve the existing 3,086-game WG casual catalogue, embeds, authentication, favorites and monetization behavior.
3. Run static checks, dependency audits and a production build after meaningful changes.
4. Keep PR #8 as a draft until the implementation is reviewable.
5. Do not merge or deploy without the owner's explicit approval.
6. The owner deploys an approved beta to the existing Vercel project; browser-test it and fix recorded issues before release.
7. Promote to v0.3.0 only after acceptance checks pass; then update Roadmap and Past Updates.

## Confirmed product direction: Fun Ground Originals
- Fun Ground Chess is the first original game and the first game targeted for Fun Ground-managed competitive play.
- Keep the existing WG Playground catalogue for casual embedded gaming. WG multiplayer approval is not a prerequisite for v0.3.0.
- Add other original games in later updates, one at a time.
- Do not present any WG embedded title as a Fun Ground-owned game or claim its iframe is integrated with Fun Ground matchmaking.
- Keep competitive game capabilities explicit and provider-neutral so future approved original games can reuse safe platform services.

## Chess modes and matchmaking policy
- **Casual:** play another player where available, or choose an AI opponent.
- **Training:** play against AI with selectable difficulty; provide a low-pressure practice experience.
- **Battle – Quick Match:** search for a real player first. After 3 minutes without a match, offer the player an AI opponent.
- **Battle – Ranked:** search for a verified real player first. After 5 minutes without a match, offer an AI opponent only as an optional switch to an unranked AI game.
- AI fallback never counts as a ranked match, ranked win/loss, leaderboard result, tournament result, competitive XP, ticket, coin or prize. It must be clearly labelled as an AI game.
- A player must explicitly accept the AI fallback; never silently substitute an AI.
- Ranked requires verified account eligibility and a real human opponent. Do not create a ranked record for an AI match.
- No private invite matches and no pre-match chat in the initial release.

## Chess gameplay and integrity requirements
- Implement standard chess rules, including legal move validation, check, checkmate, stalemate, castling, en passant, promotion, repetition and move-count draw rules.
- Use a maintained chess rules library for legal move generation and state validation; do not hand-roll incomplete chess rules.
- Treat server state as authoritative for online matches. Clients submit a move request, not a replacement board/FEN or a claimed result.
- Validate player identity, match membership, side-to-move, legal move, match status and idempotency on the server before persisting a move.
- Persist an auditable move history and enough state to restore a match after refresh/reconnect.
- Support resign, draw offer/acceptance, timeout, disconnect and bounded reconnect behavior. Final clock policy and reconnect grace period must be specified before enabling Ranked.
- Use a chess engine such as Stockfish for AI. AI difficulty must be bounded and selectable; AI moves must still pass the same chess rules validation.
- Casual and Training AI games may run without competitive rewards. Do not trust client-only AI outcomes for competitive progression.

## Competitive foundation and feature gates
- Server-only feature gates default to disabled unless the corresponding environment variable is exactly true. Never expose secrets or server gates through `NEXT_PUBLIC_*`.
- Match creation, move acceptance, result finalization and rewards must be server-authoritative and idempotent.
- Ranked requires a completed real-player Chess match and a verified result.
- Never award XP, tickets, coins, prizes or leaderboard positions from untrusted client-submitted results.
- Firestore rules must deny direct client writes to authoritative match, move, result, queue and reward records.
- Use authenticated Firebase ID tokens verified with Firebase Admin on server routes.
- Add rate limits and replay protection to matchmaking and move/result endpoints.

## Existing progression/economy decisions (not permission to activate rewards)
- Lifetime XP and player levels are permanent; no level-100 cap.
- Competitive XP resets daily. Competitive rankings are per game, with an overall normalized ranking also planned.
- Rank ladder: Bronze, Silver, Gold, Platinum, Diamond, Mithril, Fun. Players begin at Bronze; rank persists across daily resets, with maintenance checks and at most one-rank demotion for failing maintenance. Bronze cannot demote below Bronze.
- Promotion requires both an XP threshold and a competitive-performance benchmark.
- Top 10 players per rank are intended to receive daily rewards. Exact reward packages and maintenance/promotion thresholds are not finalized; previously discussed 10/50 maintenance XP and 150 promotion XP are drafts, not approved constants.
- Fun Battle rewards are intended to be XP plus a Tournament Ticket, only after server-verified human match results.
- No cosmetic rewards are planned.
- Fun Tokens are for major tournament entry. Tournament Tickets are for small tournaments. Ground Coins are exclusively major-tournament prizes and may become redeemable only after legal and payment-provider approval.
- Payments, deposits, cash-out, prize redemption and rewarded-ad earning remain disabled until separately reviewed and approved.

## Current foundation status
The branch now also contains the first client-side Fun Ground Chess build: a responsive 8×8 board, legal move handling through chess.js, Casual and Training mode selectors, three starter AI difficulty settings, check/checkmate/draw status, queen promotion, restart and undo controls. The initial AI is a lightweight local minimax opponent, not Stockfish and not a server-authoritative engine. It is a playable prototype only; it must not be used for ranked results, rewards or anti-cheat claims. The Battles hub links to /chess, Chess is in the primary navigation (including mobile), and the route is included in the sitemap. Ten Node.js regression tests cover the starting position, illegal moves, castling, en passant, promotion, checkmate, stalemate, threefold repetition, insufficient material and equal 8×8 board geometry; they are wired into CI. The reported uneven-square issue was fixed by explicitly defining eight equal grid rows as well as columns.

The following are **not yet implemented**: Stockfish-strength AI, AI-specific behavior tests, online match creation and server-authoritative move/state APIs, live match synchronization, reconnect/rematch lifecycle, the 3-minute and 5-minute fallback flow, trusted Chess result finalization, leaderboard aggregation, missions, XP/levels/ranks, and reward distribution. The current matchmaking queue's 90-second expiry values are temporary cleanup guards; replace them with lifecycle-aware rules before real matches are enabled. The latest CI run 41444253119 passed all ten Chess tests, dependency audits, catalogue checks, TypeScript and the production build. Its matching Vercel Preview deployment is READY.

## Implementation order
1. Inspect and stabilize the existing branch foundation; preserve the catalogue and existing site behavior.
2. Expand Chess domain logic and regression coverage using the maintained chess.js library (the chess-rule and board-layout regression tests are now in CI).
3. Build the responsive Chess board and Casual/Training AI flows.
4. Add server-authoritative online match creation, move validation, real-time synchronization and reconnect handling.
5. Implement Quick Match (3-minute AI offer) and Ranked Match (5-minute unranked AI-switch offer).
6. Add verified human-match result finalization, then Chess leaderboard/ranks/XP.
7. Add daily missions and Fun Battle rewards only after result integrity is proven.
8. Run full CI, review security rules and test guest/signed-in/mobile/desktop flows before proposing beta.

## Beta acceptance checks
- Existing guest browsing, search, categories, game pages, WG embeds, favorites and sign-in remain functional.
- Catalogue remains exactly 3,086 records with unique IDs and unchanged embed data.
- Chess rules tests cover special moves, illegal moves, check/checkmate, stalemate and draw conditions.
- Server rejects illegal moves, out-of-turn moves, non-member actions, stale/replayed requests and client-forged results.
- Refresh/reconnect restores the exact authoritative board and clock state.
- AI is clearly labelled; AI games never affect ranked standings, tournament results or competitive rewards.
- Quick Match offers AI only after 3 minutes; Ranked offers an explicitly unranked AI switch only after 5 minutes.
- Ranked only records human-vs-human Chess matches with verified outcomes.
- Competitive flags remain off by default; no payment, cash-out or ad-reward flow is active.
- Mobile layouts, accessibility basics and signed-out states are tested.
- No production merge/deploy occurs without owner approval.

## Dependency reproducibility
The repository currently has no committed `package-lock.json`. CI creates a temporary lockfile before install/audit, so dependency resolution can change between runs. Commit and review a lockfile before beta/production promotion so CI and Vercel install the same pinned dependency graph.

Generate it on the development branch with Node.js 22 and npm:
```bash
npm install --package-lock-only --ignore-scripts --no-audit --no-fund
npm audit fix --package-lock-only --ignore-scripts
npm ci --no-audit --no-fund
npm audit --audit-level=high
npm run check:catalog
npx tsc --noEmit
``

Commit only the reviewed lockfile to the development branch. Do not merge it to `main` without review.
